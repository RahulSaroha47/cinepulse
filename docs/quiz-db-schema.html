Relationships

Foreign Keys

quiz_attempts.user_id → users.id MANY-TO-ONE
daily_quiz_questions.daily_quiz_id → daily_quizzes.id MANY-TO-MANY (join)
daily_quiz_questions.question_id → quiz_questions.id MANY-TO-MANY (join)

Unique Constraints

daily_quizzes.quizDate → one quiz per day for all users
quiz_attempts (user_id + quizDate) → one attempt per user per day
movies.tmdbId → prevents duplicate TMDB movies
users.email, users.username → enforced at signup
Request Flows

APP BOOT DataSeeder

1
Check movies count — skip if already seeded
2
Call TMDB /movie/popular (English × 4 pages + Hindi × 2 pages)
3
INSERT ~120 rows into movies
4
INSERT 20 rows into dialogues
5
INSERT 8 rows into director_entries

POST /api/auth/signup

1
Validate email + username not taken
2
BCrypt-hash the password
3
INSERT into users with streak=0, totalScore=0
4
Generate JWT signed with secret key
5
Return {token, username, email}

GET /api/quiz/today

1
JwtFilter reads Authorization header, validates token, sets user in SecurityContext
2
SELECT daily_quizzes WHERE quizDate = today
3
If not found → generate: READ movies, dialogues, director_entries
4
INSERT 5 rows into quiz_questions, 1 row into daily_quizzes, 5 rows into daily_quiz_questions
5
Check quiz_attempts for today — set alreadyCompleted flag
6
Return questions without correctAnswer field

POST /api/quiz/submit

1
Check quiz_attempts — reject if already submitted today
2
For each answer: compare with correctAnswer in quiz_questions
3
Score = base pts + timeLeft×2 (per question) × streak multiplier
4
UPDATE users: streak++, lastQuizDate=today, totalScore+=score
5
INSERT into quiz_attempts — locks out replay
6
Return score breakdown + new streak
Design Decisions

Seed tables are read-only

movies, dialogues, director_entries are written once at startup and only ever read by QuizService. They're the raw material for question generation.

correctAnswer never leaves backend

quiz_questions.correctAnswer is stored in DB but stripped from the API response. Only checked server-side on submit — client can't cheat by reading the response.

Lazy quiz generation

Daily quiz is generated on the first GET of the day, not by a cron job. A race condition guard (DataIntegrityViolationException catch) handles two simultaneous first requests.

Denormalized streak & score

streak and totalScore live directly on the users row (not computed from attempts). This keeps the leaderboard query O(1) per user instead of requiring a SUM across all attempts.

Unique constraint prevents replay

quiz_attempts has a composite unique key on (user_id, quizDate). The DB itself enforces one attempt per user per day — no application logic needed beyond checking it.

No @OrderColumn on @ManyToMany

Removed after it caused null gaps in the questions list. Questions are shuffled before being saved so order doesn't matter — retrieval order from the join table is sufficient.
